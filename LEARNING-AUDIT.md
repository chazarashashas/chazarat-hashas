Written by reading the actual source files in this repo on 2026-09-09, not from memory of prior sessions. Where something is inferred rather than confirmed by reading the code, it's labeled as such. Where something looks fragile or wrong, it's called out plainly rather than softened.

## 1. Project Overview

Chazarat Hashas ("חזרת הש״ס" — "review of the Talmud/Mishnah") is a study-tracking app for working through all of Mishnah (the 6 sedarim, 63 masechtot, 524 perakim, ~4,181 mishnayot). It is not a text-authoring app — it doesn't store its own copy of the Mishnah text. Instead it fetches Hebrew (and, selectively, English) text live from Sefaria's public API and layers study tools on top:

- **Daily Limmud**: read today's mishnah(s) at a chosen pace (1/day, 2/day, or a full perek/day), mark it learned, and move a single sequential position forward through all of Shas.
- **Explore Shas** (`MapOfShas`): browse any seder/masechet/perek/mishnah directly, out of sequence.
- **Review**: a spaced-repetition ("Leitner box") flashcard system over whatever you've already learned.
- **Mishna Notes** (`PerekNames`): write your own one-line name and summary for every perek, plus a longer free-text notebook, plus a running list of "concepts to revisit."
- **Five practice games**: Mishna Quiz (identify a mishnah's location), Sidrei Hamishna (matching game), Seder Sort (sort masechtot into their seder), Shas Dash (arcade runner), Mishna Chazara (recall all masechet names from memory).
- **My Siyumim** (`Progress`): exposure/completion tracking at every level (mishnah→perek→masechet→seder→Shas), certificates, and a "next siyum" pace estimate.
- **Group learning**: Chevrusa (one-on-one study partner) and Chabura (any-size group, optionally rebbe-led class), with shared notes, "learned today" indicators, and encouragement ("chizuk") nudges.
- **L'Iluy Nishmat**: a distinct, separate feature — crowd-source finishing all of Shas in memory of someone, by having any number of people (accounts not required) each claim and learn specific perakim.
- **Rebbe Dashboard / Admin**: a teacher-facing view of a class's daily submissions, and a superadmin-only view of the whole user base.

Accounts (email or Google, via Supabase Auth) are optional. The app works fully signed-out, storing everything in the browser's `localStorage`; signing in layers a sync-to-cloud mechanism on top (see §4, §6) so the same progress follows you across devices. It ships three ways from one codebase: as a normal website, as an installable PWA, and as a native Android app via Capacitor.

## 2. Stack Inventory

Read directly from `package.json`:

- **Framework**: React 19.2.8 + TypeScript ~6.0.2, built with Vite 8.2.2 (`@vitejs/plugin-react` 6.1.0).
- **No router.** There is no React Router or similar in `package.json`, and none is used — see §3/§5.
- **Backend**: Supabase (`@supabase/supabase-js` 2.115.0) — Postgres database, Auth (email/password + Google OAuth), Row Level Security, and one Edge Function (`delete-account`). This is the *only* backend; there is no separate Node/Express server.
- **PWA**: `vite-plugin-pwa` 1.3.0, configured with Workbox `NetworkFirst` caching specifically for `sefaria.org/api/*` so previously-viewed mishnah text works offline.
- **Native shell**: Capacitor 8.x (`@capacitor/android`, `@capacitor/core`, `@capacitor/cli`, plus `@capacitor/app`, `@capacitor/keyboard`, `@capacitor/status-bar`, `@capacitor/splash-screen` plugins), wrapping the same Vite build for the Android app.
- **Styling**: plain CSS files (one per component), no CSS framework, no CSS-in-JS. Shared design tokens live in `src/styles/theme.css`.
- **Tooling**: ESLint 10 (flat config) + `typescript-eslint` 8 + `eslint-plugin-react-hooks`, Prettier 3.9.6. No test runner of any kind is installed — there are zero automated tests in this repo.
- **External API dependency**: Sefaria's public REST API (`sefaria.org/api/...`) is fetched directly from the browser at runtime, with no server-side proxy. If Sefaria is down or changes its API, the app's core reading feature breaks with no fallback.

## 3. File Map

*(Full per-file breakdown gathered separately and available in this conversation; summarized here by area.)*

- **`src/App.tsx`** is the entire router substitute: one `section: string` state, switched over in a large ternary to decide which screen renders. There is no `<Route>` anywhere in the codebase. Also owns: the Sidrei Hamishna game wrapper, a `?siyum=<slug>` deep-link reader, and an OAuth-error reader that parses Google/Supabase's redirect for `#error=...` so a failed sign-in doesn't silently look like nothing happened.
- **`src/data/`** is hand/generated reference data: `shas.ts` (the 6-seder/63-masechet/524-perek structure — the one source of truth nearly everything else imports), `mishnaSequence.ts` (the flat ordered list of every mishnah, plus the `mishnaKey()` function used as a lookup key everywhere), `perekNames.json`/`mishnayotCounts.json` (generated once from Sefaria via `scripts/fetchPerekNames.mjs`, not regenerated automatically).
- **`src/utils/`** holds all the hooks that are the app's real logic layer: `useAuth.tsx` (session/profile), `useCloudSync.ts` (local↔cloud merge), `useLearningProgress.ts` (completions/streak/position), `usePerekNotes.ts`, plus one hook per major feature (`useChevrusa.ts`, `useSiyumim.ts`, `useSpacedReview.ts`, `useGameStats.ts`, etc.). This directory is where almost all of the app's actual behavior lives — components are mostly rendering + wiring.
- **`src/components/`** is one directory per screen/feature, each a `.tsx` + same-named `.css` pair. `Login/LoginScreen.tsx` (847 lines) is the largest file in the app — it is both the sign-in form *and* the entire "My Account" dashboard. `DailyLimmud/DailyLimmudScreen.tsx` (679 lines) is the main daily-use screen.
- **Root-level `.sql` files** (`admin_setup.sql`, `chevrusa_security_fix.sql`, `fix_google_signup_*.sql`, etc.) are hand-run Postgres migrations — **not** an automated migration system. Nothing in CI or the build runs them. The only record that they were ever run against production is: they exist in this repo, and code comments elsewhere assume their effects exist (e.g. `useAuth.fetchProfile` has a fallback query specifically for "in case `admin_setup.sql` hasn't been run yet"). There is no single source of truth for "what does the production database schema actually look like right now" other than the production database itself.
- **`supabase/functions/delete-account/index.ts`** is the one server-side function in the whole app (Deno, uses the service-role key). It does **not** auto-deploy — pushing this file to GitHub changes nothing in production until someone manually pastes it into the Supabase Dashboard and clicks Deploy.
- **`android/`** is Capacitor-generated (Gradle project) — not hand-maintained source, regenerated by `npx cap sync android`.

## 4. Concepts in Play

These are the ideas that matter to understand this codebase; several of them are not obvious from filenames.

- **No router, no server framework.** Navigation is a `useState` string. The "backend" is entirely Supabase's hosted Postgres + Auth + RLS + one Edge Function — there is no custom server code except that one function.
- **Two separate, only loosely connected storage systems.** Every screen reads/writes `localStorage` directly (via `useLocalStorageState`), and that's *always* true, signed in or not. `useCloudSync` is a second layer bolted on top: on sign-in it fetches whatever's in the Supabase `user_data` table for that account, **merges** it field-by-field with what's already in `localStorage` (with different merge rules per field — see `mergeBlobs` in `useCloudSync.ts`), writes the merged result back to `localStorage`, and then polls every 10 seconds pushing any local changes up. Reading and writing progress data (`useLearningProgress`, `usePerekNotes`, etc.) never talks to Supabase directly — those hooks don't know accounts exist at all. This is a deliberate design (per its own code comments: "without touching the hooks that already read and write those keys"), not an oversight, but it means "is my data safe" always actually depends on both layers behaving correctly together.
- **The 10-second poll is a real, accepted gap.** Anything changed less than 10 seconds before the tab closes or the network drops has no cloud copy. `signOut()` was patched to flush synchronously first (this session's fix), but a crashed tab, a phone put to sleep, or closing the browser outright are not covered — this is not a hidden bug, it's a known and documented tradeoff in the code, but it means "did my last few minutes of learning actually save" is not something the app can promise if you don't cleanly sign out.
- **`mishnaKey()` is a load-bearing lookup key used everywhere** (completions, review schedule, notes) — it's built by string-concatenating masechet/perek/mishnah. This session found and fixed a real corruption (two literal null bytes inside the template string, likely from a bad copy/paste at some point) that silently broke every lookup using that key, and — because `completions`/`reviewState` are part of the single JSON blob pushed to Supabase's `jsonb` column, and Postgres's `jsonb` type rejects embedded null bytes outright — likely caused *any* signed-in account with review data to fail its entire cloud sync silently, for an unknown period of time before this session.
- **The `handle_new_user()` Postgres trigger is the actual account-creation logic, and it lives only in the database, not in this repo (until this session added copies of it as `.sql` files after the fact).** Every new signup — email or Google — creates a row in Supabase's own `auth.users` table automatically, and this trigger is what then creates the matching row in `public.profiles`. If the trigger throws, Postgres rolls back the entire `auth.users` insert too (same transaction) — so a broken trigger doesn't produce a broken account, it silently produces **no account at all**, with nothing in the UI to say why. This is exactly what was happening to Google sign-ups this session: the trigger only ever read `raw_user_meta_data->>'username'` with no fallback, and Google never sets that key (Google doesn't collect a username) — every single Google sign-in attempt failed at the database level for as long as this went unnoticed. There is no test, migration record, or code comment anywhere that would have caught this without literally introspecting Postgres's own catalog tables live.
- **Google's OAuth metadata shape on this project is `name` only** — no `given_name`/`family_name`, confirmed by direct query this session (`diagnose_display_name.sql`). This is a fact about how this specific Google Cloud OAuth app is configured/scoped, not a general truth about Supabase+Google — don't assume it generalizes to a different provider or a reconfigured one.
- **The claim system in L'Iluy Nishmat works without an account at all**, by generating a random `claim_token` client-side and keeping the claim reference in `localStorage`; the server-side RPCs re-verify that token rather than trusting a client-supplied user id. This is the one place in the app where meaningful write access is deliberately given to anonymous users.
- **Two kinds of "done" are tracked separately and not merged automatically**: `completions` (exposure — you read it) is the input to Progress/certificates/My Siyumim. `reviewState` (retention — you've been quizzed on it and rated yourself) is a completely separate spaced-repetition ledger layered on top by `useSpacedReview`. Marking something "learned" does not, by itself, put it into the Review queue in any special way beyond making it eligible.
- **RLS (Row Level Security) policies are the actual authorization layer for the database**, and like the trigger, they live in Postgres, not in this repo, except where a `.sql` file happens to also define them. A missing UPDATE policy on `profiles` (mentioned in a code comment in `useAuth.tsx`) was itself a bug that had to be separately fixed — the client code assuming a policy exists is not the same as it existing.

## 5. Decisions Made

Decisions actually made in code (not aspirational — confirmed by reading the file), with what drove them where visible in comments/context:

- **Local-first, cloud-as-sync-layer**, not cloud-as-source-of-truth. `useLearningProgress`'s own top-of-file comment still says "there are no user accounts yet... this is per-browser, not per-person" — a leftover from before accounts existed, and it's telling that nobody has needed to make it false: even with accounts, `localStorage` is still where every read and write actually happens.
- **Merge, never overwrite, on sign-in** — `mergeBlobs` in `useCloudSync.ts` has a distinct, deliberately-chosen merge strategy per field (some prefer local-if-non-empty, some take the max of two numbers, some take the more-recently-reviewed item, some are simple array unions). The stated goal (per its comments) is that signing in on a new device should never silently discard either side's data.
- **A device-level "reset" signal (`reset_requested_at`) beats the merge** — when a device notices the cloud copy has a newer reset timestamp than the last one it applied, it adopts the cloud state wholesale instead of merging, specifically so that an admin's or the user's own "reset my data" doesn't get quietly undone by a stale device merging its old copy back in. The accepted cost, per the code's own comment, is that this can also discard unrelated changes that device made but hadn't synced yet — a deliberate rare-edge-case tradeoff, not an accident.
- **`flushLocalDataToCloud` runs before `supabase.auth.signOut()`, not after** — a same-session fix. The ordering matters specifically because `useCloudSync`'s effect wipes local storage the instant it observes "no session," so pushing after sign-out would already be too late.
- **No PDF library for printable output** (Certificate, Print Notes) — both use `window.print()` directly with print-specific CSS, not a generated PDF.
- **No routing library** — a single `section` string. This was true from early on and hasn't been revisited even as the number of screens grew substantially; there's no comment explaining why, so this reads as inertia rather than a re-affirmed choice.
- **Sefaria's default English translation for Mishnah was deliberately rejected.** `src/utils/translation.ts` hard-codes an allowlist of specific translation versions (Koren-Steinsaltz, Silverstein/Bartenura) because Sefaria's normal default pick is from a source not considered appropriate for this app's audience — a real editorial/halachic policy decision encoded directly in application code, not just a technical choice.
- **Google sign-in intentionally allows an incomplete profile** — `signInWithGoogle`'s own comment notes a first-time Google sign-in may land with no username, "same as any profile field left blank," to be filled in later via My Account. The account-creation trigger's missing NOT NULL fallback (found this session) suggests this intention wasn't actually matched by the database constraint until the fix.

## 6. Fragility Report

Ranked roughly by how much damage a recurrence could do, based on what's already gone wrong once and what's structurally similar:

1. **Database-side logic (triggers, RLS policies, RPC functions) has no source of truth other than production itself.** The `.sql` files in this repo are a *record* of changes made, run by hand through the Supabase Dashboard — they are not applied automatically, not version-controlled against the live schema, and nothing verifies the live database actually matches what's in the repo. The Google sign-in outage this session existed specifically because a trigger was created directly in the dashboard at some point and never committed anywhere. There is no way to currently answer "does the live schema match this repo" except by manually introspecting Postgres again, the way this session had to.
2. **A silent, total sync failure is possible again with no alarm.** This session found one specific cause (a null byte inside `mishnaKey()` breaking `jsonb` upserts) purely as a side effect of debugging something unrelated — nothing in the app detects or surfaces a failed `upsert` to `user_data` in the normal 10-second poll (`useCloudSync.ts` lines ~360-364 call `.then(() => {})`, discarding any error). Any future upsert failure, for any reason, will look identical: data quietly stops syncing, with nothing in the UI to say so.
3. **The Edge Function requires a manual deploy step that's easy to forget.** `supabase/functions/delete-account/index.ts` was extended this session to support admin-initiated deletion. That change is committed and pushed to GitHub, but — confirmed by reading how this project deploys — GitHub pushes do not touch Edge Functions at all; someone has to manually paste the new code into the Supabase Dashboard and click Deploy. Until that happens, the admin-delete feature that appears to exist in the UI will fail at runtime.
4. **Auth failures are close to invisible by default.** Before this session's `initialOAuthError()` addition, a failed Google OAuth handoff (e.g. from a redirect-URL mismatch) produced no session and no error — just a silent return to a state indistinguishable from "never tried." The new handler only catches errors that come back as URL parameters; a trigger failure that Supabase reports differently, or any future new failure mode, is not guaranteed to be caught by the same code path.
5. **`useLearningProgress`'s two streak-freeze `useEffect`s both wrap their body in `Promise.resolve().then(...)` and both disable the `react-hooks/exhaustive-deps` lint rule.** This pattern (deferring to a microtask, then intentionally not listing real dependencies) is a sign the natural dependency array caused an infinite loop or a stale-closure bug at some point that was worked around rather than resolved at its root. It works, but it's exactly the kind of code that breaks confusingly if anyone touches nearby state without understanding why it's shaped this way.
6. **Nothing in this repo is tested.** `package.json` has no test runner at all. Every fix described in this session's history (the null-byte corruption, the auth flicker, the sign-out race, the trigger bug) was found by manual, live debugging — often in production, by real users hitting it first. There is no regression protection: a future change to `mishnaKey()`, `mergeBlobs`, or the auth trigger could reintroduce any of these exact bugs with nothing to catch it before a user does.
7. **The generated data files (`perekNames.json`, `mishnayotCounts.json`) have a regeneration script (`scripts/fetchPerekNames.mjs`) that is not part of any build step.** If Sefaria's data or API shape changes, these files silently go stale; nothing checks them against the live API automatically.
8. **The app assumes Sefaria's public API is available, unauthenticated, and stable in shape**, with no server-side proxy or fallback content. This is a hard external dependency for the app's single most-used feature (reading the actual text), owned by a third party.

## 7. Unanswered

Things this audit could not resolve by reading the code — either they require information only in the live Supabase project, or they're genuinely open decisions:

- **Does the live production database schema actually match every `.sql` file in this repo, in order?** Cannot be verified from the repo alone (see Fragility #1). The only way to know is to diff the live schema against these files directly in Supabase.
- **How long was Google sign-in actually broken, and how many real people hit it?** The Auth Logs UI only retains a limited window and never captured identity for a failed pre-database sign-in (only IP/request-id) — this is a hard information loss, not something more code archaeology can recover.
- **Is there currently any monitoring/alerting on Supabase (failed upserts, Edge Function errors, auth errors) at all**, or does every production issue still get discovered by a user reporting it? Nothing in the codebase configures this either way — it would live in Supabase project settings, not in this repo.
- **Explore Shas's exact opening view** (all 63 masechtot at once vs. 6 seder tiles first) and **Rebbe Dashboard's default sort** (quietest-first vs. alphabetical) are both flagged in this session's design brief as "not mine to make, ask before building" — i.e., genuinely unresolved product decisions, not something derivable from the code.
- **Whether the admin-delete Edge Function has actually been redeployed** to Supabase yet (Fragility #3) — this audit can see the code is written and pushed to GitHub, but cannot see the live Edge Function's deployed state from here.
- **Whether `.env.local`'s Supabase keys are the same across local dev, and production (Vercel)**, or whether they've ever diverged — this audit only read that the file exists and which two variables it defines, not its values, and has no visibility into Vercel's own environment variable configuration.
